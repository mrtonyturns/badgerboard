## Open — needs a product/billing decision

- **The first failed renewal locks the account.** `customer.subscription.updated` writes `past_due` as soon as Stripe marks the subscription past due, so the lock comes before the retry grace period that `invoice.payment_failed` intends (`stripe-webhook.js`). Decide what grace period you want.
- **Upgrade prorations are billed at renewal.** Upgrades use `proration_behavior: 'create_prorations'` (pending invoice items), and cancelling immediately drops them. Consider `always_invoice` plus `invoice_now` on cancel (`update-subscription.js`, `downgrade-to-free.js`).
- **Trial vs paid ranking crosses plan families.** Every Action plan outranks every Candidate plan. So a c_campaign payer given an a_monitor trial is downgraded in practice (`_entitlements.js:205`, `tiers.js:623`).
- **Weekly auto-regeneration ignores the owner's current plan.** Downgraded or expired accounts keep getting paid AI refreshes (`auto-regenerate-dossiers.js`).
- **The dashboard countdown counts 24-hour periods.** `dueMath.js` still does this, while Elections and GamePlan now use calendar days. `tests/r2a.test.mjs` pins the current behaviour.

## Open — lower severity, not yet fixed

- **District caches can be written with client-supplied names or text.** Every user reads these caches (`research-district-history.js`, `research-district-events-background.js`).
- **SSRF:** `enrich-prospects-background.js` fetches user-set candidate websites without blocking private or link-local addresses.
- **No limits on the X feed.** `fetch-candidate-x-feed.js` has no rate limit or plan gate.
- **The AI lock can be bypassed.** In `candidate-ai-lock.js`, candidates with a null `created_by` can be toggled by anyone, and `ai_access_notes` is writable directly via PostgREST.
- **Stale digest.** `monitoring-digest.js` can send last week's digest if this week's refresh failed.
- **Monthly and yearly repeats drift.** A task due on the 31st becomes the 30th, then the 28th (`recurrence.js`). Fixing this needs an anchor day stored with the rule.
- **The Scout 2-candidate cap trigger isn't race-safe** (no advisory lock).
- **The migration chain can't replay from scratch.** `door_knock_lists` and some columns exist only in the legacy `migration_v2.sql` / `migration_v5_*.sql`, and the baseline's `USING (true)` dossier policies are only dropped by legacy v5.
- **Possible arbitrary SQL execution.** `admin-setup-candidate-storage.js` calls `rpc/exec_sql`. If that function exists in production with default grants, any signed-in user could run arbitrary SQL. Check it.
- **1000-row reads without stable ordering:** `countVotersInDistrict` (`dashboard/shared.jsx`) and `DistrictDashboard.jsx`'s `.limit(5000)`.
- **Global beta switch starts as `true`** until `app_settings` loads (`tiers.js`). This affects the UI only; the server re-checks.
